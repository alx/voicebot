# Text-Message Support — Design

**Date:** 2026-07-07
**Status:** Approved

## Goal

Let group members *type* to the bot, not just send voice notes. A text message in the
configured group gets a text reply, generated by the same reply logic the voice
pipeline uses — for both backends (direct LLM and the SillyTavern/Trico route).

## Decisions

- **Trigger:** every text message in the configured group (the group is dedicated to
  the bot). No mention prefix or command syntax required.
- **Reply medium:** text only. No TTS, no status messages — one reply message.
- **Backends:** both `LLM_BACKEND=direct` and `LLM_BACKEND=sillytavern` work.
- **Approach:** extend the Python pipeline with a `--text` mode (Approach B).
  Reply logic (backend switch, system prompt, narration stripping) stays in one
  place, `src/pipeline.py`. Rejected alternatives: replying directly from Node
  (duplicates prompt/backend logic in JS); building the persistent worker first
  (bigger scope; `--text` ports to a worker trivially later).

## Node side (`bot/`)

- `bot/index.js`: the `message_create` handler gains a text branch. Messages with
  `type === 'chat'` and a non-empty, non-whitespace body are enqueued on the
  **same queue** as voice messages. Sharing the queue is required: the SillyTavern
  bridge drives a single conversation and must never handle two jobs concurrently.
- **Echo protection generalized:** today only voice replies are registered in
  `sentReplyIds`. A `sendTracked(chat, content, options)` helper wraps every
  `chat.sendMessage` call in both handlers and records the sent message id in
  `sentReplyIds`, so the bot's own outgoing messages (text replies *and* the
  voice flow's status messages) never re-trigger handling. Without this, the
  "every text message" trigger would loop on the bot's own replies. Messages
  typed by the owner from the linked phone remain processed (documented
  self-test behavior).
- New `bot/text-handler.js` (mirrors `voice-handler.js`, smaller):
  1. Reject over-length bodies (> `TEXT_MAX_CHARS`, see below) with a friendly
     message, before spawning Python.
  2. Run `python -m src.pipeline_cli --text "<body>" --json` via the existing
     `runWithTimeout` with `PIPELINE_TIMEOUT_MS`.
  3. Send `result.llm_response` as a single text message via `sendTracked`.

## Python side (`src/`)

- `src/pipeline_cli.py`: the positional `audio_file` becomes optional and mutually
  exclusive with a new `--text <message>` flag (exactly one must be given). Text
  mode skips audio validation and instead enforces `TEXT_MAX_CHARS`. JSON output
  keeps the same envelope: `{"success": true, "llm_response": ..., "timing": ...}`
  — no `transcription` or `output_audio_path` keys in text mode. Error output is
  unchanged (`{"success": false, "error": ..., "error_type": ...}`).
- `src/pipeline.py`:
  - **Lazy STT:** the Whisper model load moves out of `__init__` into a
    `_ensure_stt()` called at the top of `transcribe_audio()`. The Piper model
    existence check likewise moves into `synthesize_speech()`. This makes text
    mode fast (no ~2–4s model load) and is a behavior-preserving no-op for the
    voice flow (models load on first use, same errors raised).
  - New `run_text_pipeline(text) -> dict` runs only the reply step: the existing
    `LLM_BACKEND` switch selects `query_sillytavern` (which already applies
    `_strip_narration`) or `query_llm`. Returns `{"llm_response", "timing"}`.
- `src/config.py`: new `TEXT_MAX_CHARS` (default 1000), env-overridable, exported
  alongside the audio limits so Node can read the same value from `.env`
  (`bot/config.js` gets the matching entry).

## Error handling & edge cases

- Python failures produce the same `success: false` JSON; Node sends the
  configured error status message when `ENABLE_ERROR_NOTIFICATIONS` is on.
- Ignored inputs: empty/whitespace bodies; non-`chat` message types (stickers,
  images, locations, media captions); messages from other chats when
  `VOICEBOT_GROUP_ID` is set; messages whose id is in `sentReplyIds`.
- Timeout: a hung Python process is killed by `runWithTimeout` as today.

## Testing

- **pytest:** `run_text_pipeline` happy path for both backends (HTTP mocked at
  the `requests` level, matching existing tests); empty-reply error; CLI arg
  validation (`--text` XOR positional file); `TEXT_MAX_CHARS` enforcement;
  lazy-STT regression check (constructing the pipeline in text mode does not
  load Whisper).
- **Node (`npm test`):** text branch enqueues on the shared queue; bot-sent ids
  are skipped (no echo loop); over-length rejection; error path sends the error
  status message.

## Out of scope

- Persistent Python worker (future work; `--text` becomes a worker job type).
- Voice replies to text input; per-user rate limiting; handling media captions.
